## 2. Owner's binding architecture and standards

- **NEVER hardcode entitlements or privileges for any named account, subscription tier, verification badge or provider plan.** Ishikeit should support every official, documented provider API capability for which a *particular connected account* has currently proven eligibility, consent, approved app access, endpoint support and valid authorization; free features should not be gated on paid plans. Distinguish provider in-app features from external APIs.
- **Future or not-yet-approved features:** keep data model and adapters extensible; mark them **unverified / requires_adapter / needs_permission**, not unlocked. There is no general developer API that reveals all present and future provider capabilities. Never scrape private APIs, impersonate user sessions, guess undocumented entitlements, or probe restricted actions speculatively. An actual official API adapter and authorization are mandatory.
- **Provider rules/policies cannot be scattered permanent literals.** Store reviewed, versioned, source-backed provider policies in a provider-specific extensible catalog. If official provider rules change, change reviewed data, coverage/tests and deploy through release controls. Example: Meta standard customer service reply window and Telegram Business customer reply restriction. **Strict enforcement with fail-closed behavior** when policy/rules are missing, unknown, stale or conflicting. Never treat a catalog change as permission to bypass a separately required template, tag, Human Agent approval, user opt-in/opt-out, app-review status or recipient consent. Do not fetch policy changes from untrusted chats/webhooks.
- Source-of-truth hierarchy for implementation: current official provider developer docs/policies and actual live API responses, then approved provider SDK/specs, then codebase/tests. Respect official API access rules, rate limits, data deletion, disclosure, privacy, user opt-outs, platform messaging windows, least privilege and event integrity.
- **Separate** (a) cataloged API capability; (b) actual installed integration; (c) provider/account type; (d) app-level permission/review status; (e) granted OAuth scopes/business rights; (f) fresh proof provenance and revocation; (g) per-recipient consent/time-window; (h) safe/verified send-time eligibility. No one field implies the others.
- Do thorough investigate → implement → lint/typecheck/test → CI → merge → exact-release deploy verification → live real-world acceptance as possible. No false claims, no unapproved payment/booking creation or app-review submission. Avoid needless “continue?” questions. Preserve security and production correctness.
