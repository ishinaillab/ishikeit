# Meta unknown-outcome operator reconciliation — 2026-10-29

## Purpose and limits
Ishikeit cannot reliably infer whether Meta accepted a message after a lost HTTP response or process crash. The durable pre-send fence deliberately quarantines uncertain sends instead of retrying them. This operator workflow is an **attestation ledger**, not a Meta provider verification or message release mechanism.

## Authenticated operational routes
Both routes exist only when OPS_METRICS_TOKEN is configured. Use an authorized secure backend client over HTTPS; never put an operational bearer token into a URL, document, browser page, or chat.

- GET /ops/meta/unknown-outcomes?limit=25 — returns total/reviewed/unreviewed and up to 50 bounded cases with only outbox UUID, channel, operation, fence time, terminal time and review state. No customer, account, recipient, message body, authorization or Graph error text is returned. Unauthenticated requests 401; malformed limits 400.
- POST /ops/meta/unknown-outcomes/:outboxId/review — JSON with `disposition` = `followup_required` or `reviewed_do_not_resend`; `evidence` = `provider_record`, `manual_thread_review` or `customer_confirmation`; and `operatorTag` (3–48 alphanumeric, underscore, dash or period). The operatorTag is SHA-256 hashed; it is a supplied label, not cryptographically authenticated identity. The token authenticates access to the operational API.
- POST returns `recorded` after first insert, `already_recorded` for identical repeated submissions, 409 for conflicting submissions, or 404 for unrelated or ineligible outbox rows. The first attestation is immutable; there is no UPDATE or DELETE route and no manual send/retry route.
- The operator MUST verify evidence in the relevant authorized Meta business inbox or provider records. Selecting `provider_record` attests that a human checked records; it is not independent proof from Meta. Never mark a case as delivered based on HTTP 200 or a Messenger watermark alone.

## Handling an unresolved case
1. Authenticate over a private, non-cacheable connection. List only unknown-outcome cases. Do not expose payloads, recipients or raw bearer tokens.
2. Review provider conversation and native business inbox using authorized tools. Check any independently correlated delivery receipt and its exact account/channel/message ID if available. If missing, treat the outcome as unknown.
3. Record `followup_required` when human outreach/decision is necessary, otherwise `reviewed_do_not_resend` after the operator has completed review and consciously decided no automated resend.
4. No attestation changes `outbox.dead_lettered_at`, `meta_send_started_at`, queue leasing or the provider. Human follow-up must obey current channel policy, customer window, consent and handoff restrictions; it is **not** an instruction to requeue an old action.

## Storage and compliance
The private `public.meta_outbound_reconciliations` table is keyed to the existing outbox UUID and contains only an enumerated disposition, enumerated evidence basis, operatorTag hash and reviewed timestamp. RLS is enabled; PUBLIC, anon, and authenticated grants are revoked. No sensitive message content is copied into the ledger. Privacy deletion of an outbox row cascades to its attestation.

Applied Supabase migration version: `20261029092718_meta_outbound_unknown_reconciliations`, tracked by ishinaillab/ishikeit-db PR #13.

## Known remaining limits
- The operational bearer is shared and can authenticate a request, but an operator-supplied tag does not independently prove individual reviewer identity. A future identity-aware RBAC/signed admin session is needed for strong per-person audit attribution.
- The new route does not reconstruct a missing provider message ID or prove exactly-once delivery.
- Cases marked followup_required remain terminal dead letters and require an explicit separate human follow-up process. No customer message is generated by this workflow.
- Do not bulk-replay historical dead letters; do not activate WhatsApp appointment reminders or Meta Require App Secret.
