# Priority 3 — durable protected schema migration release lease (2026-11-21)

**Status: LOCAL-ONLY REVIEW, not merged, not deployed, not approved for production.** GitHub issue #284 shared-write HOLD and the separate Meta App Review NO-SUBMISSION instruction remain in effect.

## Safety defect and local correction

The prior protected `.github/workflows/priority3-protected-schema-release.yml` used GitHub Actions serial concurrency, two owner-reviewed environments and a 44→45 migration manifest check, but its hosted `supabase db push --yes` still ran **without first acquiring and durably arming** a shared PostgreSQL release lease. A timed-out GitHub worker or Supabase CLI operation could leave an unknown migration outcome while a later independent Hostinger deployment had no corresponding `pending_external_step='schema_migration'` record blocking it. The existing application controller already used the same private release-owner table to fence Hostinger builds. Both operations must share the release scope.

New isolated `scripts/priority3-protected-schema-lease.mjs` uses the existing `PostgresPriority3ReleaseFence` CAS primitive and shared scope `ishikeit_priority3_production`. It validates exact approved app/DB main SHAs and the reviewed 45-version local SQL manifest, checks the remote 44-version prefix and protected GitHub branch heads, acquires one secret-digest generation-fenced lease, independently rechecks live branch heads and lease state, and **persists `pending_external_step='schema_migration'` before starting any hosted Supabase CLI push**. The same protected workflow builds the exact Node24 TypeScript source and runs this controller only in owner-reviewed `apply`, with no direct SQL-push bypass.

A completed CLI exit alone never frees a release. The controller reads all 45 remote versions and the enabled, least-privileged native outbox trigger, rechecks GitHub main heads, renews the same owner lease, and only then records `verified_schema_migration_at`, advances the fencing generation and clears the pending step. A lost provider response, GitHub drift, canceled job, timeout, stale lease, schema mismatch or disabled trigger **retains the durable hold**, including after lease expiration. An independently approved `reconcile` operation **never resubmits the migration**; it accepts only exact verified 45/45 and the active trigger, and can clear only an **expired** matching schema-migration hold. An active holder, wrong SHA or pending `app_deploy` cannot be reconciled by schema recovery. Initial release `preflight` remains read-only and never acquires a lease.

The protected GitHub schema workflow now allows manual `preflight`, `apply`, `verify`, and `reconcile` with unchanged two-owner-environment gates, first-attempt/actor checks and shared serial concurrency group. `preflight`/`apply` require exactly 44 hosted versions, `verify`/`reconcile` require 45. Updated CI covers both mock/state-machine tests and real PG17 lease/e2e tests.

## Remaining external acceptance blockers

This controller is **not** an externally universal lock: a privileged DBA, Hostinger hPanel/API operator or any independent production writer outside the protected workflow can still bypass a PostgreSQL application lease. It requires owner-approved exclusive release handoff, no concurrent admin deployment, authenticated GitHub environment and secret readback, exact Hostinger website Git/auto-deploy disabled proof and a dedicated short-lived token. The current live Supabase project still has 44 migrations, zero native account connections and no live owner-provider revocation/readback acceptance; draft PR #304/#305 remain unmerged.
