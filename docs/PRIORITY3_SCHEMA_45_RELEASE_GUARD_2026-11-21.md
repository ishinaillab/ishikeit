## Root cause and correction

The previously staged Hostinger release controller checked `supabase_migrations.schema_migrations` for exactly **44 applied migrations**, although the reviewed native tenant outbox integrity guard is **migration 45**, `20261118222000_priority3_native_outbox_write_fence.sql`. That accepted the old schema and rejected the correctly migrated schema. A new focused Node24 regression test was deliberately **RED** before the fix: the old controller admitted a proposed deployment against 44.

The revised `scripts/priority3-protected-hostinger-release.mjs` has one reusable, read-only `assertProtectedNativeSchema(db)` guard executed **before release lease acquisition and Hostinger POST**. It requires: exactly 45 applied versions, the exact 45th migration timestamp, and PostgreSQL system-catalog evidence that `ishikeit_native_outbox_write_fence` is enabled on `public.outbox`, executes the expected `SECURITY INVOKER` function, and cannot be executed by `anon` or `authenticated`. A missing, disabled, public executable, security-definer or unexpected migration count fails closed. This check does not itself apply a migration or enable sending.

The protected schema workflow `.github/workflows/priority3-protected-schema-release.yml` now expects precisely 45 versioned files from the pinned DB main SHA. Its `preflight` and `apply` modes require the existing exact 44-version hosted prefix; `verify` requires the complete 45-version history. After an authorized `apply`, independently read back all 45 versions and the same active least-privileged database trigger. The workflow uses official stable Supabase CLI 3.2.0 and retains `--skip-vault`, no role/seed reset, no automatic triggers, two owner-reviewed environments and the serial privileged-release group. Both stages additionally require a fresh owner-originated `workflow_dispatch` run attempt 1, checking both original actor and current triggering actor through GitHub expression gates and runtime environment variables.

The original schema workflow used ordinary Python `assert` for its live database checks. Those assertions disappear under `PYTHONOPTIMIZE=1`; this fail-open condition was **observed RED** using synthetic forged PostgreSQL URLs. Both embedded Python stages now use explicit `require(...)` checks that do not depend on optimization. The database URL guard allows only the exact Supabase project direct host or the approved Singapore Supavisor pattern, matching the exact PostgreSQL username/database and excluding unsafe URL query/fragment options. No password values were printed or used in local testing.
