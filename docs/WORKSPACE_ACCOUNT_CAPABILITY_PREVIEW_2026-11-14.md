## Current evidence, authoritative sources and method

- The live-capability **facts** system already exists: `src/persistence/account-capability-facts.ts`, migration `0009_provider_account_capability_facts.sql`, and `src/policy/provider-contract.ts` with reviewed `src/policy/provider-contracts.json`. The provider-backed write paths previously recorded Instagram OAuth/professional account access, Messenger Page readback, and Telegram Bot API Business rights. This change creates **no** new grant writer, no DB migration, no data backfill, no extra permissions and no network probes.
- Per-account evidence is source-scoped, revocable and expiring; evidence tied to another provider/account is never combined. `evaluateAccountFeature()` would require current verified facts and, for Instagram, a verified Business/Creator account type. This account-type field is not proved for every workspace connection; the preview therefore leaves such feature eligibility **unverified**. It does not infer account type from usernames, paid-plan labels, verified badges or a manually selected plan. The readback labels a requirement as met only under the reviewed catalog and with fresh matching proof. Missing, denied, conflicting or expired evidence is never turned into sending permission.
- Official API framework: [Instagram Platform API docs](https://developers.facebook.com/docs/instagram-platform/), [Telegram Bot API BusinessConnection](https://core.telegram.org/bots/api#businessconnection), [Meta platform policy](https://developers.facebook.com/devpolicy/), and [OWASP authorization cheat sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html). Provider rules and catalog should be updated only through separately reviewed versioned changes; not guessed from paid plans. The user requirement in #206 specifically distinguishes Free/Premium/Business on Telegram and personal/Creator/Business/Meta One subscriptions for Instagram. It does **not** authorize private/unofficial APIs.
- This is a **saved evidence snapshot**, **not** proof that Meta app 1042452472116584 has advanced permissions or a Tech Provider approval. The provider app was last read back with `NO_SUBMISSION`, privileges `[]`, and owner App Review hold #169. No live provider account or user acceptance was exercised in this change.

## Implementation

1. `PostgresWorkspaceConnectionRegistry.capabilitiesForAdministrator()` executes in **one PostgreSQL transaction**: validate workspace and connection UUIDs, lock and verify current active owner/admin membership and workspace, read the exact existing connection under `FOR SHARE`, then read at most 64 latest capability records by the **provider and provider_account_id sourced from that database row**, never from browser query parameters. No PostgreSQL RLS grants are changed; all reads are server-owned.
2. `presentAccountCapabilityEvidence()` uses only versioned reviewed feature contracts for which per-account facts can be displayed. It returns feature ID, reviewed evidence status, explanation and required-key names plus source kind, latest observed/expiry time and granted/denied/expired/unknown status. It does not return raw provider proof bodies, sourceReference, app secrets, bearer tokens, refresh tokens, credential account IDs or cross-tenant data. Feature `available` means **only** that the reviewed catalog's account evidence requirements were met, not that Ishikeit has operational tenant messaging authorization.
3. `PrivateBrowserAuthService.workspaceAccountCapabilities()` re-verifies fresh Supabase AAL2 and that the bearer belongs to the same current BFF session; the registry independently checks current owner/admin membership. BFF GET `/app/auth/workspaces/:workspaceId/connections/:connectionId/capabilities` enforces exact first-party host, fetch-site, existing Secure HttpOnly session and strict UUID parsing. It replies privately with no-store CSP, generic error on denial and no provider-secret-bearing logs.
4. The Channels page gets a **View verified permissions** control on each connection. Its result is fetched only on demand; client verifies the exact workspace, connection, provider, provider account and registry generation before rendering as `textContent` in DOM elements. Cross-account or stale-generation responses show a generic error and are not displayed. The page explicitly states this is saved provider evidence, not a message-send or subscription permission, and no paid-plan features are inferred.
5. No change to routing, inbound/outbound workers, authorization policy for message dispatch, any provider token store, subscriptions, account registration, webhook setup, live Meta/Telegram/TikTok connections or owner MFA.
