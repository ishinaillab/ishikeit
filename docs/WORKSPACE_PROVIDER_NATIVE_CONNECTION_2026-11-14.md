# Priority 3 — private, owner-initiated, provider-native workspace linking (Instagram adapter; 2026-11-14)

## Precise release boundary

This is the FIRST provider-specific implementation of Priority 3, **not** completion of all providers and **not** activation of tenant messaging. It adds a private Instagram Login connection flow to the existing AAL2-protected Ishikeit workspaces. It is guarded by the explicit **off-by-default** `BROWSER_INSTAGRAM_CONNECT_ENABLED=false`. The feature must not be enabled until the owner registers the **exact new** HTTPS callback with the Meta app, confirms production permissions, and approves the expected app/account and auth flow. This code cannot simulate or grant owner authorization on the owner's behalf.

No existing legacy Instagram/Meta/WhatsApp/Telegram/TikTok credentials or live webhook subscriptions are imported, rewritten, disconnected or replaced. All existing provider messaging continues along its existing path. No new environment secrets or database migration; uses existing secret-key-encrypted `oauth_credentials` and existing validated workspace connection/intent tables. The encrypted per-connection namespace `workspace-instagram` with a unique connection UUID key avoids overwriting legacy `instagram` credentials. The generic OAuth store explicitly blocks unscoped tenant-namespace `latest`, `list`, `put`, and alias upserts; its server-only exact-connection transaction writer is used exclusively after the tenant membership/ownership checks. A row in `ishikeit_account_connections` (even status `connected`) never authorizes a send: live provider permission, app eligibility, recipient consent, generation-fenced tenant processor and dispatch remain separate Priority 4 acceptance gates.

## Trust and permissions

1. Only a currently authenticated private **Secure, SameSite=Strict, HttpOnly** browser session can start, finish or confirm. BFF verifies live Supabase Auth principal, exact Supabase session, enrolled factor and `aal2`, then DB checks the workspace is ACTIVE and the member is active **owner or admin**, under row locks. Viewer, agent and foreign workspace do not have a permit.
2. Start `POST /app/auth/workspaces/{workspaceId}/connections/instagram/start` enforces exact Host, Origin, Fetch-Site and BFF CSRF. The server selects fixed Instagram Login app ID, provider endpoint and exact canonical `https://apps.ishinaillab.com/app/auth/connect/instagram/callback` redirect. It stores an unguessable 10-minute one-use state in the existing DB intent, bound to actor, real session, workspace, provider and provider app; separate cryptographically random 10-minute browser nonce lives ONLY in a Secure, HttpOnly `__Host-ishikeit-ig-connect` Lax cookie. No supplied account ID, username, provider host, OAuth app or redirect is trusted.
3. Instagram provider redirects cross-site via authorization code. The exact callback GET **never exchanges credentials or changes the database**, and uses no third-party scripts or resource links. It serves a strict same-origin/no-referrer document; JS strips the code and state from browser URL, fetches CSRF inside same-origin BFF context and submits a POST with only code and state. The Lax nonce and Strict BFF session remain HttpOnly. The callback POST uses the original AAL2 live session, current owner/admin role, exact app/redirect, state and browser nonce for **one-use atomic intent consume**. No unknown/replayed/mismatched grant may claim another workspace.
4. Only the **official** Instagram Login token exchange and Professional identity readback are used: short-lived code→token, check the actual granted `instagram_business_basic` and `instagram_business_manage_messages` scopes, exchange long-lived grant, `GET /me?fields=user_id` with official Graph endpoint. The immutable numeric Professional ID, not a mutable handle, is the claimed account. Neither grant nor provider response is sent to the browser. Meta public App Review availability is NOT inferred from returned scopes.
5. `PostgresWorkspaceConnectionRegistry.linkVerified` atomically inserts the unique provider-account ownership claim and the distinct AES-GCM-encrypted grant under `workspace-instagram/<connectionUUID>`, marks exactly one consumed, unclaimed session intent as claimed and audits the operation **in the same PG17 transaction**. If a store or ownership claim fails, the entire transaction rolls back. New status **verifying**; no actual sends or provider subscriptions are activated.
6. After owner reads the pending ID in Channels, `POST /app/auth/workspaces/{workspaceId}/connections/{connectionId}/activate` revalidates strict BFF AAL2/CSRF/role, then reads the *exact* encrypted credential with a server-only scoped lookup, requires unexpired messaging scopes, calls a **fresh live Instagram /me readback** to prove exactly the original Professional account and activates only the previously `verifying` record with correct fixed app/credential binding, incrementing its generation and writing audit. Replays, revoked membership, mismatched identity or changed app are denied. `connected` means internal registry proof, **not permission to dispatch**.
7. The neutral Channels UI exposes `Connect Instagram` and `Confirm Instagram activation` only for owner/admin when the server flag says it is available. Uses existing style, text-only DOM construction and status updates; hides stale workspace items on workspace switch/sign-out, never stores access token or provider nonce, and explicitly warns that automation stays disabled.

## PKCE and provider reality

OAuth 2.0 Security BCP RFC 9700 recommends PKCE S256 for **confidential** clients and requires public clients to use PKCE. The internal `PostgresWorkspaceConnectionIntents` already creates a per-attempt S256 code challenge and verifier. However, in the reviewed Meta Instagram Login authorization-code endpoint and client exchange contract no verified support for `code_challenge` and `code_verifier` has been established. Sending those as extra fields without documented support would risk a broken provider OAuth flow or an invalid security claim. For this confidential Instagram Login integration the code therefore deliberately uses the documented app-secret code exchange and cryptographically random browser-bound one-time `state` plus independent cookie nonce and exact redirect. **Do not claim Instagram PKCE support or BCP-complete code-injection protection** until the provider documents and verifies PKCE end-to-end. The shared intent PKCE facility remains available for providers that support it.
