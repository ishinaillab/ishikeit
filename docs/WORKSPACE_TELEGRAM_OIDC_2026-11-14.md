# Priority 3 — Telegram OIDC identity + Telegram Business connection readback (2026-11-14)

## Scope and status
Adds a second, genuinely provider-native owner proof to Ishikeit: modern **Telegram Login with OpenID Connect (OIDC)** and **RFC 7636 PKCE S256**. Unlike Instagram Login's confidential-client app-secret-only flow, Telegram documents the S256 code challenge and verifier explicitly. This is an **OFF-BY-DEFAULT**, isolated, first-party browser account-linking implementation under `BROWSER_TELEGRAM_OIDC_ENABLED=false`. It is NOT the Telegram Business bot's webhook router, a request to connect BotFather's bot, a grant to message a third party, a migration of the existing studio Telegram Business connection, or a tenant send permission.

### Verified provider contracts (authoritative)
- [Telegram, Log In With Telegram](https://core.telegram.org/bots/telegram-login) explicitly recommends the new OIDC code flow with S256 PKCE instead of the archived iframe widget. The authorization endpoint is `https://oauth.telegram.org/auth`; token endpoint `https://oauth.telegram.org/token`; JWKS `https://oauth.telegram.org/.well-known/jwks.json`; issuer `https://oauth.telegram.org`.
- The owner **must** register the exact `https://apps.ishinaillab.com/app/auth/connect/telegram/callback` and allowed origins in their chosen bot's **@BotFather → Login Widget** settings, obtaining a provider-issued **Client ID and Client Secret**, separate from the already operational Bot API token. Application startup fails closed when the configured OIDC client ID doesn't equal the Business bot ID from its trusted token.
- Telegram's signed OIDC `sub` is an opaque identifier and must NOT be assumed equal to Telegram Bot API `user.id`. Telegram's official example uses different `sub` and `id`. The `profile` scope provides a separately signed numeric `id` claim. Require `openid profile`, a valid RS256 signature via the fixed Telegram JWKS, exact issuer/audience/nonce/iat/exp, and a valid numeric `id` before identity binding. Missing/invalid `id` fails closed. Never rely on a mutable username.
- [Telegram Bot API](https://core.telegram.org/bots/api) `getBusinessConnection` returns `id`, immutable `user.id`, `is_enabled`, optional `rights.can_reply`. Rights changes remain dynamic. Telegram authorizing OIDC is NOT evidence the owner connected the bot to Business or that the bot has reply rights.

### Login and tenant boundary
- Existing strict Secure HttpOnly same-origin BFF session, *fresh* Supabase Auth AAL2/TOTP enrollment proof, original session UUID, current active workspace and live owner/admin membership are required for start, completion and activation. An agent or viewer cannot claim an account. Every POST requires exact Host, Origin, Fetch-Site and current BFF CSRF. Owner cannot supply actor, OAuth application/client ID, callback URI, token destination, claims, grant scopes, or provider endpoint.
- `POST /app/auth/workspaces/{workspaceId}/connections/telegram/start` uses the existing durable one-use 10-minute `ishikeit_connection_intents` table to generate 32-byte state and independent 32-byte browser nonce. A server-derived HMAC code verifier yields Telegram-documented S256 code challenge. OIDC authorization `scope=openid profile`, `state`, `nonce=state`, `response_type=code`, `code_challenge_method=S256`. The separate nonce is stored only in an HttpOnly Secure Lax `__Host-ishikeit-tg-connect` cookie, bound to one exact workspace; no token, nonce, PII or state appears in logs.
- Cross-site provider GET `/app/auth/connect/telegram/callback` does **not** redeem or persist credentials; it serves only strict no-store/no-referrer first-party HTML and JS under a no-third-party strict CSP, immediately strips the code from browser history before same-origin CSRF-bound POST to `/app/auth/connect/telegram/complete`. The BFF Strict session cookie and independent Lax nonce are required, then the exact same original Auth session, principal, workspace, BotFather app key and one-use intent are verified and atomically consumed before contacting the token endpoint. No redirect/XSS/host injection.
- Confidential-client token exchange uses **fixed** provider URL, Basic client authentication, 8-second deadline, bounded response, exact redirect and server-held PKCE verifier, no redirects. Valid provider-signed, unexpired OIDC `id_token` provides the signed numeric `id` for immutable Telegram Bot API user matching; OIDC `sub` is not substituted. No Telegram OIDC access token is persisted, logged or sent to the browser. The tenant-scoped provider account is atomically linked as `verifying` in existing private PG registry with unique account claim, consumed session-bound intent and audit, never sharing tenant tokens or modifying legacy Telegram sender.
- OIDC login **does not activate Business messaging**. A second owner action `POST /app/auth/workspaces/{workspaceId}/connections/{connectionId}/telegram-business`, with a candidate Business connection ID, verifies the owner's **current** AAL2 session and membership, then calls `getBusinessConnection` with the server-owned exact bot token. It REJECTS absent/disabled Business connections, absent `can_reply`, or provider `user.id` not identical to the signed numeric OIDC `id`; the incoming candidate ID alone is never proof. Under PostgreSQL row locks, one private transaction confirms original bot-app binding, null original provider/credential binding and matching immutable user, then records the unique Business connection ID, marks status `connected`, increments generation, audits. Competing tenant claims, stale/replayed activations and unexpected bot identity are rejected.
- Even a `connected` private registry record is NOT a production send permit. Tenant events remain parked by the previous #289/fenced worker; actual policy, capabilities, signatures, generation and recipient messaging permissions must be independently verified during Priority 4 cutover. **No live Telegram or Meta provider settings/tokens/webhooks are changed by this feature's code.**

### Operations / remaining acceptance
- **Default remains disabled.** Before any activation: review BotFather's registered exact redirect+origin and OIDC client secret/ID, confirm the operational bot is the exact app owner expects, perform genuine AAL2 BFF sign-in, provider OIDC consent, signed ID-token negative tests, fresh Bot API business readback for a real owner, ensure subscription/rights, verify foreign-tenant/revoked-owner/no-reply cases in owner-controlled production, and then enable only after explicit owner approval.
- Telegram Business connection IDs originate in Bot API `business_connection` webhook updates or privileged provider readback. The current explicit form does **not** guess an ID or create a Telegram Business connection on behalf of the owner. Improve UX later through **signed webhook-observed and independently provider-readback** connection discovery; do not infer ownership by only a username, timing, or account plan.
- Full Priority 3 still requires owner acceptance and relevant other providers' genuinely native verified connection mechanisms (Messenger/WhatsApp/TikTok account-scoped entitlements). Priority 4 must not start prematurely.
- Telegram OIDC uses the maintained `jose@6.2.17` v6 ESM JWT/JWKS implementation pinned in `package-lock.json`, verified compatible with Node24. Strict verification permits only explicitly configured RS256 signing, never `none` or attacker-specified public JWKS/issuer/algs.
- See [OAuth 2.0 Security BCP RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html), [OpenID Connect Core](https://openid.net/specs/openid-connect-core-1_0.html), [OWASP OAuth2](https://cheatsheetseries.owasp.org/cheatsheets/OAuth2_Cheat_Sheet.html), [Telegram Business bots](https://core.telegram.org/bots/api), [Supabase Auth MFA](https://supabase.com/docs/guides/auth/auth-mfa), [PostgreSQL 17 explicit locking](https://www.postgresql.org/docs/17/explicit-locking.html).
