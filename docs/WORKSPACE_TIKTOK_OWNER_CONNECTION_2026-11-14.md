# Priority 3 — TikTok account-holder native connection (default-OFF, 2026-11-14)

## Intended behavior and safety boundary

Native TikTok **organic account-holder** authorization for an Ishikeit workspace. It is **not** TikTok advertiser/Marketing API authorization; it MUST use the account-holder authorization URL registered by the developer for the app and the `/tt_user/oauth2/token/` code exchange that returns an app-scoped immutable `open_id`. This code does **not** authorize messages, claim platform approval, automatically subscribe webhooks, switch ingress routing, process inbound messages, or send any requests that change TikTok data.

The entire feature is guarded by **`BROWSER_TIKTOK_ACCOUNT_CONNECT_ENABLED=false`**, including the private browser routes and UI. Enabling it requires an actual owner-approved app and registered exact HTTPS redirect `https://apps.ishinaillab.com/app/auth/connect/tiktok/callback/` with trailing slash, plus the known developer dashboard account-holder authorization URL `TIKTOK_ACCOUNT_HOLDER_AUTHORIZATION_URL`. The portal URL is never invented from `TIKTOK_BUSINESS_AUTHORIZATION_URL` or user input, and the server accepts only vendor-owned HTTPS origins. Secrets remain server-side in protected env.

## End-to-end trust model

1. Owner/admin logs in to the private Ishikeit BFF (HttpOnly/Secure/Strict opaque session, current verified Supabase `aal2`) and opens the **Channels** panel. Only server-enabled owner/admin sees `Connect TikTok`. The start POST validates same-origin Host/Origin/Fetch-Site and anti-CSRF, verifies the actual privileged Supabase session and its active workspace membership in PostgreSQL, creates random 10-minute one-use state plus independent HttpOnly/Secure/Lax nonce cookie. It uses a developer-app-configured TikTok account-holder URL with that state. No provider credential or nonce enters client JavaScript or the authorization URL.
2. TikTok returns a **one-use authorization code** to the exact registered callback. Callback GET never exchanges tokens, changes the DB, or sends provider API requests; it serves a no-store, no-referrer document with strict CSP that strips the code/state from browser history. The frontend posts code/state to the same-origin BFF with CSRF. The nonce remains HttpOnly. The intent consume revalidates session `aal2`, owner/admin membership, exact app+workspace+redirect, state, nonce and unexpired claim. A replay cannot exchange a second token.
3. The server reuses existing `TikTokOAuthClient.exchangeAuthorizationCode` for the official `tt_user/oauth2/token/` endpoint (not the Marketing advertiser token API). It validates the returned immutable, app-scoped `open_id`, nonempty provider scopes, 24-hour token lifetime and distinct refresh token. It atomically creates a private `verifying` workspace registry record and encrypted, isolated `workspace-tiktok/<connectionUUID>` token + refresh token in the **same PostgreSQL transaction** as the unique provider-account ownership claim, one consumed session intent and audit. A failing write, duplicate ownership or stale intent rolls everything back. Generic global tenant-token `latest`, `list`, `put` are refused. No legacy TikTok credential is overwritten.
4. An **independent** owner/admin activation POST rechecks AAL2, workspace membership and CSRF, uses only the specific connection UUID to decrypt the stored grant, and requires an unexpired short-lived token, a fresh provider token-info scope readback + a fixed official `/business/get/` Advanced Access account readback. Any failure/mismatched identity or missing rights refuses activation; it never infers Business Messaging API developer eligibility from `has_advanced_access`. The registry independently checks original app+credential/account binding and active owner in one transaction and increments generation.
5. The UI explicitly states that `connected` is an **internal account identity** state only. Messaging must remain disabled until the provider developer app has completed TikTok's independent data security and privacy approval, scopes, account eligibility including 18+ conditions, live permission and recipient policy; that future tenant-aware dispatch is Priority 4. Current live integrations, subscriptions and credentials remain untouched.

### PKCE limitation

The shared one-use intent can generate S256 for PKCE-capable providers, but the TikTok **Business Account Holder** developer-portal authorization endpoint and `tt_user/oauth2/token/` contract have **not** been confirmed to accept standard RFC7636 `code_challenge` and `code_verifier`. Supplying unsupported fields could break code exchange or create a false protection claim. This confidential-client flow uses server app-secret exchange, exact redirect URI, cryptographically random 10-minute state, independent cookie-bound nonce, one-use session- and workspace-bound intent, and strict browser CSRF. It does **not** claim PKCE support for this provider until officially established. This caveat remains for acceptance/security review.
