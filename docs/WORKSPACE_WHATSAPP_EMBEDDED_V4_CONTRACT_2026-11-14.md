## Official source contract as of November 2026

1. [Meta Embedded Signup overview (updated October 29, 2026)](https://developers.facebook.com/documentation/business-messaging/whatsapp/embedded-signup/overview): Versions **v2 and v3 deprecated October 15, 2026**. Build against current stable **Embedded Signup v4** and do not silently use beta-preview v5. Meta's WAAC/Messaging account split is rolling out. Existing `waba_id` is still the **Messaging account** ID; `phone_number_id` is the separate business phone identity. The WAAC ID is not safely substituted until Meta makes that new API contract available.
2. [Meta Embedded Signup implementation (updated October 27, 2026)](https://developers.facebook.com/documentation/business-messaging/whatsapp/embedded-signup/implementation): v4 uses **Facebook Login for Business with JavaScript SDK**, requires a configured allowed HTTPS domain and explicit `config_id`. `FB.login` with `response_type: "code"`, `override_default_response_type:true`, `extras:{setup:{}}` delivers `authResponse.code`. The exchangeable code lasts only **30 seconds**, so server exchange must start immediately. Independently capture and validate the `WA_EMBEDDED_SIGNUP` session event; never trust its `waba_id` and `phone_number_id` as ownership proof. Do not log browser callback raw codes or account secrets.
3. [Onboarding customers as Tech Provider (updated August 5, 2026)](https://developers.facebook.com/documentation/business-messaging/whatsapp/embedded-signup/onboarding-customers-as-a-tech-provider): only after proper Tech Provider/Tech Partner status, exchange the browser code server-to-server via **GET `/oauth/access_token`** to a business integration system user token. Tech Provider uses business tokens, not generic User tokens. Required Cloud API permissions are `whatsapp_business_management` and `whatsapp_business_messaging`.
4. [Business phone numbers](https://developers.facebook.com/documentation/business-messaging/whatsapp/business-phone-numbers/phone-numbers) and [Client phone numbers](https://developers.facebook.com/documentation/business-messaging/whatsapp/solution-providers/manage-phone-numbers): use **GET `/{messaging_account_id}/phone_numbers`** with the customer-scoped token to confirm the exact `phone_number_id`. Signed app identity and token scope alone do not establish ownership of a client-supplied phone number. Subsequent phone registration and webhook subscription are separate owner-approved **mutating** provider operations, not part of this proof.
5. [OAuth 2.0 Security BCP RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html): The future JS SDK integration needs same-site session CSRF protection, one-time server intent bound to original `aal2` owner/workspace/app, strict known Meta postMessage origin filtering, replay prevention, and final tenant registry lock/generation fencing. Do **not** claim that the vendor's JS SDK supports PKCE or that a BFF-generated `state` is provider-round-tripped without verifying the actual SDK contract.

## Server-only provider proof library

- Accepts only validated numeric Messaging account ID and business phone ID candidates, and bounded Meta code. Uses the exact, server-configured Meta app ID/secret and Graph version, HTTPS Graph host, redirect-disabled GET calls with an 8-second timeout and bounded JSON (32 KiB). It never follows provider-supplied next-page URLs; it constructs strict, bounded cursor requests.
- Exchanges the ephemeral code first, then inspects the resulting token with Meta `debug_token`: issuing app, validity, required permissions, expiry and data-access expiration. Requires `BUSINESS_INTEGRATION_SYSTEM_USER` as a **conservative provisional token-type allowlist** derived from Meta's terminology, not a verified live example of the exact `debug_token.data.type` enum. Before production enablement, confirm this field against an actual owner-authorized Meta sandbox grant; if the provider returns a different enum, correct it using authoritative evidence, never expand the allowlist speculatively.
- Checks the exact Messaging account `GET /{waba_id}?fields=id`, then the authorized phone list `GET /{waba_id}/phone_numbers` using the business token plus `appsecret_proof`, and finally a direct `GET /{phone_number_id}?fields=id`. Refuses mismatched account, missing phone, malformed cursor, overly broad/invalid provider response. Limits locally retained grant validity to the earlier of server 60-day reauthorization bound and the provider-reported token/data-access expiry; no permanent messaging entitlement is inferred.
- Returns a server-only candidate token and exact asset IDs for a **future** transactionally scoped enrollment operation. The class itself never stores this token or exposes it to a browser. There is no tenant claim and no caller can send WhatsApp messages based on its output.
