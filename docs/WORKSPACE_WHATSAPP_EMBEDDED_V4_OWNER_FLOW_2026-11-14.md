# Priority 3 — WhatsApp Embedded Signup v4 owner-bound browser flow (2026-11-14)

## Scope, prerequisites and unreleased state

This work builds a **draft, default-disabled** tenant-bound WhatsApp Embedded Signup v4 owner BFF and a separate confirm-by-provider-readback action. It is **not** a live WhatsApp onboarding acceptance or permission to send messages. The feature is enabled only with an owner-configured `BROWSER_WHATSAPP_EMBEDDED_V4_ENABLED=true` and `META_WHATSAPP_EMBEDDED_V4_CONFIG_ID`, the existing encrypted credential vault key, verified AAL2 browser login and confidential Meta app secret. Neither owner-level Meta App Review nor actual Tech Provider eligibility has been verified; **owner hold #169 is still in force**, so do not turn this on or attempt live client signup.

- This candidate intentionally stacks **after PR #296** (WhatsApp v4 read-only business-token/asset proof). It does not alter the original canonical Windows checkout, existing provider deployments or old studio WhatsApp tokens.
- Source: `src/auth/workspace-whatsapp-embedded-v4.ts`, `src/auth/whatsapp-embedded-v4-proof.ts`, `src/auth/private-browser-auth.ts`, `src/persistence/workspace-connections.ts`, `src/auth/oauth-store.ts`, `src/http/private-browser-auth-routes.ts`, `src/http/private-whatsapp-embedded-v4.ts`, `src/http/private-browser-ui.ts`, `src/processes/http.ts` and `src/config/env.ts`.
- No schema migration needed: the existing verified workspace registry stores both the **Messaging account ID** in `provider_connection_id` and exact **business phone ID** as `provider_account_id`; credential encrypted under a new isolated `workspace-whatsapp/<connection UUID>` key. Legacy default connection and provider routing remain completely untouched.

## Verified official vendor contract, not conjecture

[Meta Embedded Signup overview, updated 2026-10-29](https://developers.facebook.com/documentation/business-messaging/whatsapp/embedded-signup/overview) and [implementation, updated 2026-10-27](https://developers.facebook.com/documentation/business-messaging/whatsapp/embedded-signup/implementation) define the stable **v4** JS SDK browser flow. Versions v2/v3 were deprecated on October 15, 2026. The SDK returns a short-lived 30-second `response.authResponse.code`; a separate JSON `window.message` session event `{type:"WA_EMBEDDED_SIGNUP",event:"FINISH",data:{waba_id,phone_number_id,...}}` provides the **candidate** IDs. The browser sends both to our same-origin BFF; neither is accepted as asset ownership until the official [Tech Provider business-token exchange](https://developers.facebook.com/documentation/business-messaging/whatsapp/embedded-signup/onboarding-customers-as-a-tech-provider) and Graph `debug_token`, exact Messaging account and phone membership+identity reads succeed.

**Account model nuance:** Meta is separating phone-identity **WhatsApp account (WAAC)** from templates/billing/subscriptions **Messaging account**. For the documented rollout, `waba_id` continues to identify the Messaging account; `phone_number_id` is the phone identity. Never substitute a guessed future WAAC ID. The JS SDK flow in this draft allows only the documented standard `FINISH` event with both IDs. Coexistence `FINISH_WHATSAPP_BUSINESS_APP_ONBOARDING` or other flows cannot silently downgrade to standard signup and remain unsupported until separately documented/tested.

## Security and user flow

1. Owner/admin begins from the current Ishikeit workspace Channels view, which displays **Connect WhatsApp** only when explicitly enabled. Navigation uses a first-party workspace UUID path, with no OAuth code or access token in query strings, localStorage or browser history. A dedicated BFF HTML screen isolates the Meta SDK under its own restrictive CSP (`connect.facebook.net` script, fixed Facebook frame/connect origins, no `unsafe-inline`) rather than weakening the ordinary dashboard.
2. The first-party script obtains a CSRF token from the authenticated BFF and POSTs `/app/auth/workspaces/:workspaceId/connections/whatsapp/start`. The server revalidates Supabase AAL2 and enrolled factor, exact current session owner/admin membership and app config; its one-time PostgreSQL intent binds the exact owner, workspace, provider, Meta app/config, original session, opaque 32-byte state and distinct Secure HttpOnly SameSite=Lax 32-byte browser nonce (stored only in host-only cookie). No random provider `state` parameter is assumed: Meta's v4 JavaScript SDK documented callback does **not** echo an application `state`; our state is an **internal same-origin, CSRF-bound proof**, never a claimed provider OAuth response.
3. On a deliberate user click, `FB.login` invokes exact owner-configured `config_id`, `response_type:"code"`, `override_default_response_type:true` and `extras:{setup:{}}`. First-party JS accepts JSON session events only from exact `https://www.facebook.com` or `https://web.facebook.com`, rejecting dangerous suffix origin matches. The standard successful FINISH event must have both numeric IDs. The SDK code is transient RAM only and paired with these IDs within an 8-second bound; Meta itself enforces the 30-second exchange deadline. The UI never logs secrets, sends a browser token or asks for the app secret.
4. The completion POST must carry the original internal state, Meta code, candidate Messaging account ID and phone ID under exact Host/Origin/Fetch-Site and CSRF with the original host-only BFF session and nonce. One-use PostgreSQL intent consumption rechecks the original AAL2 owner/workspace; a replay, role revocation, foreign cookie or wrong app cannot exchange the provider code. The server exchanges Meta code first, validates the business token issuing app/allowed token type/scopes/expiry, reads the exact Messaging account and its assigned phone, and checks the direct phone identity.
5. Only after all provider checks, one PostgreSQL transaction inserts the globally unique WhatsApp phone-account claim for the workspace, encrypted per-connection business token, consumes the original intent claim and audits ownership. Status is `verifying` and **never sends or subscribes**. The **Confirm WhatsApp number** owner action rechecks current AAL2, owner/admin role, exact bound phone ID + Messaging account ID, original app/config/credential UUID, encrypted token, fresh `debug_token` scopes and asset identity, and atomically sets the registry status to `connected` with a fenced generation increment. This status **still does not authorize live tenant routing or any WhatsApp send**.
6. The new private `findBindingForAdministrator` registry read is server-only, requires the current live owner/admin membership, and exposes the original Messaging account + credential IDs only to trusted verification code, never the public connection inventory. Legacy generic OAuth credential `list/latest/put` cannot enumerate or overwrite `workspace-whatsapp` grants.
